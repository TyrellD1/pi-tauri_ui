01

The answer in plain terms

Yes, use an extension when you want Pi to delegate as a named, model-callable tool. Core Pi has no built-in subagent manager or universal child-agent protocol. Running another Pi from bash works, but the extension is what makes delegation structured and repeatable.

The reference pattern is: the parent calls subagent, the extension selects a Markdown agent profile, a separate Pi runs the task, and the extension returns its result. The official example supports one child, several children in parallel, or a sequence of children. A skill can teach when to delegate; it does not create the runtime tool.

For this app, build a small Pi package from that pattern and use persistent pi --mode rpc children. Let Rust own their processes, sessions, limits, and event routing. Keep a terminal runner in the package so the same delegation tool also works outside the app. This is an app integration we would build, not a feature already exposed by Pi.

The first useful release should let a parent launch a child, show that child inline, open its live transcript and available thinking, stop it, and reopen its saved transcript after restart. Add parallel and chain execution on the same foundation, then background delegation and continuation.

02

What subagents do, and what they do not do

A child gets its own model context. By default, pass the task and the files or findings it needs, rather than copying the whole parent conversation. The parent receives a compact result. This helps long searches and specialist reviews stay out of the parent’s working context. Parallel read tasks can also finish sooner.

A separate context is not a separate filesystem. The official example uses the parent’s working directory unless another one is supplied. Two workers can edit the same files. Our first version should allow several readers but only one writer in a shared checkout. Worktree-based writers are a later feature.

Show missing usage/cost as unavailable, not zero, and identify Pi/provider-reported estimates as such. Each child makes its own model requests. Delegation can increase total tokens, latency, and process memory. It can lower parent context use; it does not guarantee lower cost or better answers. Report child usage separately and sum it with parent usage without counting returned summaries as another child run.

“See its reasoning” means show the thinking blocks and deltas that the provider exposes through Pi. Some models expose none or redact them. Show “This model did not provide visible thinking” when needed. Do not invent or infer private reasoning.

06

Keep one owner for each process

The parent remains the exact CLI harness. Its extension registers subagent and sends a structured launch request to a Rust broker. Rust creates and controls child Pi RPC instances. The extension waits for the result and returns it through Pi’s normal tool-result path.

The broker connection is new app code. On macOS, use a Unix-domain socket in a private runtime directory. Future Windows support can use a named pipe. Do not add invented commands to Pi’s stdin protocol or write ad hoc JSON to Pi’s stdout. The socket carries app messages; each Pi stdin/stdout still carries native Pi RPC only.

Pass a socket path, protocol version, and per-parent capability token only to app-owned Pi processes. Bind the token to the real parent instance generation and canonical session. Validate every launch/control request against that binding. Use private socket permissions, bounded frames, and no credentials in logs or persisted manifests. This is local ownership validation, not a sandbox against other processes running as the same user.

Outside the app, the same extension selects a standalone runner that owns persistent child RPC subprocesses. It forwards child dialogs to the terminal parent’s UI and renders progress through normal tool updates. Its cap is local to that terminal parent; only the desktop broker can enforce a limit across all app chats. Never silently switch to the fallback after a connected broker disappears, because that can launch duplicates.

A terminal-launched child run can be imported as saved history using the same manifest format. Live control of independent terminal-owned children is a later attach protocol, not part of V1.

Proposed interfaceContract
Extension → brokerhello, launch, cancel_run, and subscribe_run. Every frame has version, request ID, parent capability, and launch/run identity. Broker replies with admission/state/result events; no polling.
UI → Rustpi_list_subagent_runs, pi_get_subagent_history, pi_subagent_stop, pi_subagent_steer, pi_subagent_follow_up, and an exact-owner dialog reply. Controls resolve a saved child ID to its current live owner; they cannot spawn implicitly.
Rust → UIA separate subagent-event envelope contains schema version, parent session, run/child ID, boot/generation, sequence, and original Pi event. Root pi-event behavior stays scoped to roots.
Payload limitsProposed starting limits: 16 KiB UTF-8 model-facing result per child, 64 KiB metadata frames, and 100 transcript messages per page. Native Pi message payloads have a separate validated limit sized for existing attachments; preserve explicit truncation markers and full canonical history.

A child is a session; a delegation is a run

Validate the schema marker before rendering child rows; keep unknown or legacy details in the normal generic tool view. Give each tool invocation a durable runId, and each child a durable childId. Repeated calls to “scout” are different children. Store the parent’s Pi session ID, canonical file, assistant entry ID, and tool-call ID at dispatch. These fields bind the row to the right chat and the right branch.

Find the parent assistant entry by its actual tool-call ID in the session branch. Do not assume the current leaf is that assistant message: a sibling tool can append metadata while parallel tools execute. A process instance ID is temporary. Pair it with an app boot ID and generation for live control, and never use it as the saved chat ID. Pi allocates its session filename; read get_state.sessionFile rather than guessing a UUID filename. Store task/role intent first, then attach the returned session identity before the first model prompt.

The runtime and process rules

Desktop budget: at most 6 live Pi processes in total, including parents and children. Start with at most 2 active children globally, and at most one shared-workspace writer. These are proposed hard limits, stronger than the current lazy-reaping target. Do not add a second independent child pool that silently doubles the limit.

Before admitting a run, evict only eligible idle processes. Protect active turns, parents awaiting owned foreground children, children waiting for a user response, and the visible conversation. Reserve a child slot before the parent commits to waiting. If all slots are protected, return a clear capacity error or an explicitly cancellable bounded admission request. Never leave six parents waiting for children that cannot start.

Give each app-owned Pi a supervised process group on Unix, so forced termination can clean up owned tool subprocesses too. A future Windows implementation needs the equivalent job ownership. Never kill a saved PID after restart without validating its creation identity and ownership. All process and pipe waits happen outside pool/registry locks. Slot release wakes queued work through events. A hung stdin write uses the existing 30-second deadline and retirement path. Runtime deadlines and kill grace periods are one-shot timers only while work is active, and must be cancelled on completion. No idle sweeper, periodic status probe, or elapsed-time ticker.

StepRequired behavior
1. AdmitValidate the parent token, profile, cwd, tool policy, and launch identity. Persist queued children. Resolve capacity without deadlocking their parents.
2. StartSpawn the resolved Pi executable with --mode rpc, a dedicated session directory, and the normal cwd/resources. Apply role prompt, model/thinking, and an exact active-tool policy before the first child prompt.
3. Protect profilesLoad user profiles by default. Only read project profiles when the parent has project trust and the chosen scope permits it. Hash/snapshot the selected profile. Do not treat prompts as an OS sandbox.
4. Prevent recursive spawningV1 forbids nested delegation. The child policy disables subagent and other delegation tools across built-ins and extensions, and the broker rejects nested launch requests. Keep useful ambient extensions only when the role allows their tools.
5. StreamSplit JSONL on LF only, with optional CR stripping. Route text, exposed thinking, tool activity, queues, and dialogs under the child identity. Keep reader tasks draining even when no child inspector is visible.
6. SettleUse agent_settled, not the first agent_end. Then inspect errors/stop reason and final output. A settle event alone does not prove success. Stop waiting only after retries and queued continuations are done.
7. ReturnPersist terminal state first. Resolve exactly one parent tool result with a bounded useful summary and typed references. A lost socket or parent process becomes interrupted, not an unreported success.
8. ReapRetain saved sessions. Idle live processes are reaped on pool access after 15 minutes, subject to the shared cap. Opening a completed transcript should usually read history without spawning a process.

The stock example’s --tools flag is not enough to establish an exact reader profile when ambient extensions add tools. Our child-policy extension uses the supported active-tool APIs to resolve the full allowed set and applies it before prompt admission. Include custom tools in the policy; reject a role requiring an unavailable tool. “Reader” means no bash/edit/write or other mutation tool unless the user explicitly enables one.

V1 child models inherit the parent. Keep the repository’s current set_model/set_thinking fan-out to every live process and spawn defaults. Per-role fixed models are useful, but require a later binding policy and an AGENTS.md change so global fan-out cannot silently overwrite them. Child views show the actual effective model.

Control, recovery, and delivery

SituationConcrete rule
Parent stopAbort the parent and cancel its owned foreground run. Remove queued children, abort active child RPC sessions, then terminate processes that fail to settle within a grace period. Check actual process exit, not merely whether a signal was sent. Preserve transcripts and per-child cancellation states.
One child stopAbort only that child. Parallel siblings continue. Chain successors become skipped/cancelled according to dependency, never “Done.” The parent receives an explicit partial-failure result.
Dialog reply after navigationReply using captured (bootId, instanceId, generation, sessionFile, requestId), never the visible chat scope. A stale reply fails visibly and must not spawn or target a replacement process.
Steer and follow-upResolve the exact live child, then use native RPC. Accepted messages appear in its transcript/queue. A completed child has no live steering target; continuation requires an explicit new prompt after restoring its session.
RetryCreate a new attempt linked by retryOf. Keep the previous task, result, failure, and session. A chain retry can reuse previous completed step summaries only when explicitly selected.
App restart / child crashOn clean app quit, stop app-owned processes and settle receipts. After a crash, reconcile known process ownership on startup; do not assume kill_on_drop proves all descendants died. If survival cannot be proved, mark interrupted and require explicit recovery before resuming. Never spawn a second writer automatically.
Parent process diesCancel owned foreground children and preserve interruption state. A later reopened parent can inspect results, but the old pending tool callback cannot simply be recreated. Resuming/delivering any unfinished result must be explicit and idempotent.
Reopen saved childRead the canonical session branch with bounded pagination. Restore task/model/state and available thinking. Do not concatenate every JSONL record across abandoned branches. Missing files show a recoverable explanation.
Event gap / reconnectSubscribe first, fetch a snapshot plus watermark, then apply only newer buffered events. A sequence gap triggers an on-demand snapshot. No polling loop. Every frame has ownership/generation so stale events are ignored.
Async delegation, laterReturn a receipt immediately, then deliver one completion notification to the originating parent session. Keep a persisted delivery key and acknowledgment so reconnects do not repeat or lose results. This needs its own tests and does not come free from RPC.

Begin with foreground delegation: the parent’s tool waits while its children work, yet the app still lets you switch chats and inspect them. That already supports real background viewing without detached autonomous jobs. Add async delegation only after delivery receipts and parent liveness are reliable.

For async delivery, prefer the originating parent extension’s supported message API with explicit follow-up behavior. If its process is gone, save a pending receipt and deliver after that exact session is opened. Do not inject a completion into whichever chat happens to be visible. A completion notification belongs in model context only once.

A detailed implementation sequence

Use small working changes. The paths below are proposed; they do not exist yet unless listed in the repository audit. Each step has a reviewable outcome and a gate. Build the minimal single-child experience before broadening orchestration.

01 · CONTRACT AND COMPATIBILITY

Prove the Pi extension and define the schema

Create the local Pi package, agent loader, schema marker, launch identity, and fixture events. Adapt the bundled example’s conventions and retain attribution. Target installed Pi 0.85.1; verify imports and supported RPC commands from that version. Record context input rules: fresh child task by default, no automatic parent-history copy.

Gate: no-model startup proves the tool and command load; one deliberate terminal smoke test proves a reader result returns to the parent. No duplicate subagent registration.

02 · UNDERLYING PI

Implement a persistent standalone RPC child

Add the terminal runner with native RPC framing/correlation, dedicated child session storage, exact tool policy, inherited model/thinking, and prompt handoff. Forward exposed text/thinking and tool progress through bounded normal updates. Bridge supported child dialogs to the parent’s terminal UI. Make AbortSignal cancel the actual process, with a one-shot hard-kill fallback.

Files: runner-rpc.ts, child-policy.ts, bundled reader/worker profiles, fake RPC-child fixtures.

Gate: saved child session and task survive terminal restart; cancellation ends the child; malformed output, hung writes, missing models, and dialog cancellation are explicit failures. No idle timers. Reader profiles cannot call mutation or delegation tools.

03 · DESKTOP SUPERVISION

Connect the extension to the Rust process pool

Refactor transport code into a reusable RPC-instance module. Add the local broker, capability handshake, idempotent launch handling, exact-owner commands, child admission, and parent-disconnect cancellation. Separate visible-root navigation from process lookup so child activity cannot set the selected cwd/session or overwrite the root’s recent-session choice.

Files: src-tauri/src/{rpc_instance.rs,subagent_broker.rs,subagent_runs.rs}; smaller command wiring in main.rs; package broker adapter.

Gate: a parent tool causes Rust to start one real child. Text/thinking events retain child ownership; result reaches the parent exactly once. Six protected parents return capacity failure rather than deadlocking. Both child and parent process counts respect the shared budget.

04 · DURABLE HISTORY

Persist parentage and make runs recoverable

Add atomic manifests, transition journals, parent custom entries, branch provenance, cursor-based transcript reads, and saved delivery/attempt state. Store children outside flat root-session listing. Rebuild a bounded index on demand and reconcile interrupted runs at startup. Preserve terminal-run metadata for read-only import.

Files: subagent_runs.rs, package persistence helpers; new pi_list_subagent_runs and pi_get_subagent_history Tauri commands.

Ship inline child rows and the inspector

Extend the conversation reducer to preserve supported tool details. Add a subagent store, stable child rows inside a tool group, parent breadcrumb, transcript inspector, collapsed thinking, and paged tools. Route child deltas to their own reducer. Keep root selection, focus, drafts, and scroll positions stable.

Files: src/{conversation.ts,subagents.ts,subagent-view.ts,main.ts,style.css}; index.html panel slot; src/dev-preview.ts.

Gate: clicking a child shows its own task and live transcript. Switching parent chats never mixes children. Reopened history has the same clickable rows. Light/dark, narrow screens, keyboard access, and 200-line tool output work.

06 · CONTROLS AND ATTENTION

Finish stop, steer, queues, and child dialogs

Replace current-scope dialog replies with captured owners for parents and children. Add Stop child, Stop parent and its foreground children, child steering/follow-up, per-child queue state, retry attempts, and attention badges. Keep optimistic acceptance distinct from confirmed delivery; preserve failed drafts.

Files: dialog/event paths in main.ts, broker commands and reducers; preview and regression fixtures.

Gate: replies after navigation reach only their original process; stale replies fail; stopping one child leaves siblings running; stopping a parent clears its subtree. This completes the first useful single-child desktop release.

07 · ORCHESTRATION PARITY

Add parallel readers and sequential chains

Add grouped task admission and chain dependencies. Preserve task order even when children finish out of order. Use the app-wide child cap; enforce one writer per shared cwd. Chain only compact previous results, stop on failed dependencies, and show skipped steps. Preserve partial results and per-child usage.

Files: package tool schema/orchestration, supervisor scheduler, grouped inline rendering, preview fixtures.

Gate: two parallel readers stream independently, one failed child is visible, and a chain starts each successor only after its predecessor settles successfully. Multi-parent runs cannot bypass caps.

08 · CONTINUATION AND ASYNC, AFTER V1

Add explicit continuation and reliable completion delivery

Let a completed child reopen as an RPC session for a new prompt without stealing another live session. Keep the original run and record the continuation relationship. Add async receipts and exact-parent wake-up delivery only after recovery tests pass. Add role-specific model bindings, opt-in context fork, nested agents, and isolated writer workspaces as separate changes.

Gate: a completion is delivered once to the intended parent, including reconnects; a new continuation is not mistaken for the original finished task. Any worktree allocator follows this repo’s GitButler rules and captures the actual cwd. Terminal-live attachment remains a separate feature.

First release boundary: phases 1–6 give one persistent, visible, controllable child per delegation. Phase 7 brings the official single/parallel/chain experience into the desktop. Phase 8 adds longer-lived agent work after the foundation is proven.
