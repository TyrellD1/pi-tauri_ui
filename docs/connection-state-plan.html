Per-chat connection state + manual reconnect

Implementation plan for pi-tauri_ui · item #5 of the idle-survival work · CodeG-inspired

1. Problem

Today the connection between the UI and each pi --mode rpc process is implicit. There is no visible state for it and no manual recovery: if a chat's process stalls, dies, or goes deaf, the UI either spins forever or wedges a flag (sendInFlight, navigating). The only recovery the user has discovered is quitting and restarting the whole app. Items 1–4 (visible-chat reap exemption, bounded stdin writes, stuck-flag watchdog, listener re-registration) cap the damage; this plan removes the class: make connection explicit, visible, and manually recoverable per chat, the way CodeG does with its per-session status + Reconnect.

2. Goals / non-goals

Goals

A user can always answer: is this chat connected? — from the sidebar, without opening it. Any non-connected chat offers a one-click path back that resumes (history is on disk; never restarts the conversation). Stalls surface as state with an action, never as a dead UI. Background chats report their state transitions quietly (dot + toast, as today).

Non-goals

No heartbeat polling (event-driven only — liveness is inferred from traffic + explicit failures). No auto-retry storms (one resume attempt per user action; settings fan-out stays as-is). No change to the pool cap / reap policy beyond what 1–4 set.

3. Design

3.1 State machine (per chat)

unknown → connecting → live ⇄ responding
              ↓              ↓     ↓
            dead ←──────── stale ──┘
(resume from any non-live state returns to connecting)
StateMeaningSource of truth
unknownNever contacted this run (fresh boot, unopened row)Frontend default
connectingSpawn/ensure in flightFrontend (command outstanding)
liveProcess answered recently; idle or workingAny successful command or event within N min
respondingRun in flight (existing runningSet)agent_start → agent_settled
staleNo traffic for X min while chat open, or watchdog trippedFrontend inference (timestamps only)
deadProcess exited / retired / command failed hardinstance_disconnected, retire, spawn failure

3.2 Where state lives

Rust (source of truth for process facts): new pi_pool_status command returning {instances: [{id, cwd, session, streaming, lastActiveMs, retired}]} — pure snapshot, no spawning, no sweeping side effects beyond the existing lazy sweep. The existing instance_disconnected event already covers death; add the retire reason (reaped vs write-stall vs crashed) to its payload so the UI can word the recovery correctly.

Frontend (mirror + inference): connByChat: Map<rowKey, {state, since, detail?}>. Updated on: command success/failure (connecting → live/dead), stream events (→ responding/live), watchdog trip (→ stale), disconnect events (→ dead). Never polled; refreshed on open, on demand (status button), and on any transition event.

3.3 UI

  • Sidebar row badge: today's blue pulsing dot means responding. Add quiet siblings in grayscale: hollow dot stale, ✕-ish or faded row dead, nothing for live/unknown. Blue stays reserved for "working" — the one color exception already granted.
  • Header status pill (button): for the visible chat only — Live / Responding… / Stale — Reconnect / Disconnected — Reconnect. Clicking opens a small panel: session file path, process age, last traffic, model, and the Reconnect button.
  • Failed-turn strip: classify the failure kind where known and dock the matching action under the composer: transport/timeout → Retry; process dead → Reconnect & retry; model/auth rejection → open Settings. (Today: one generic retry card.)
  • Reconnect semantics: always resume — re-ensure the scope (respawn only if the process is actually gone), reload history from disk (free and authoritative), re-apply drafts. Never new_session. If the dead process had an un-settled run, its partial turn is already in the session file as stop=aborted and renders as today's quiet Turn stopped.

3.4 Triggers

  • Automatic: opening a stale/dead chat re-ensures (already happens via scoped commands — keep, but route through the state machine so the pill shows connecting instead of a bare spinner).
  • Manual: Reconnect button (header pill, row context, failed-turn strip). One attempt per click; failure returns to dead with the reason shown.
  • Never: background auto-reconnect loops. A dead background chat waits for the user.

4. Backend work items

  • 1. Add retire reason to instance_disconnected (reaped | write-stall | crashed).
  • 2. Add pi_pool_status snapshot command (no spawn, no sweep side effects).
  • 3. Confirm ensure failure modes are all Err (never hang): audit every await for a timeout — should already hold after item 2 of the 1–4 work.
  • 4. Unit tests: status snapshot shape; reason propagation.

5. Frontend work items

  • 5. connByChat store + transitions (command results, stream events, watchdog, disconnects).
  • 6. Sidebar badges for stale/dead (grayscale; blue stays responding-only).
  • 7. Header status pill button + detail panel + Reconnect wired to resume.
  • 8. Failed-turn classification strip under the composer.
  • 9. Route auto-ensure on open through the state machine (connecting visible).
  • 10. Preview mocks (pi_pool_status, reason-tagged disconnects) + regression checks: kill visible process → pill shows dead → Reconnect resumes same chat + draft.

6. Edge cases

  • Sleep/wake: timers (watchdog) may fire spuriously on wake; treat the first post-wake transition as stale, not dead — one cheap command re-validates.
  • Crash mid-run: partial turn persists as stop=aborted; resume shows it + offers retry. Matches today's Esc/switch rendering.
  • Trust prompts (pi 0.25+): a fresh process in an untrusted folder may block on trust instead of answering RPC. Classify as its own failure kind with a "review trust" action rather than a generic timeout (CodeG built dedicated UI for this).
  • Deaf listener: if events stop but commands succeed, state inference degrades to command results; the visibility-change re-listen (item 4) stays as backstop.
  • Reaped-while-visible: impossible after item 1 (visible exempt) — listed so nobody reintroduces it.

7. Verification (no app-QA gaps this time)

  • kill -STOP <pi-pid> to simulate a stalled child → send must fail into retry within ~30s, pill must show stale, Reconnect resumes.
  • kill -9 <pi-pid> mid-run → instance_disconnected(crashed) → dead badge + strip → Reconnect resumes with partial turn visible.
  • 15-min idle on visible chat → process alive (exemption holds); on background chat → reaped silently, reopen respawns.
  • ?dev=1 regression covers 10 (mocked kill → dead → reconnect → same chat + draft).

8. Open questions

  • Should stale exist as a distinct state, or is live-vs-dead with "last active Xs ago" enough? (Lean: keep it — it drives the only automatic re-validation.)
  • Per-chat model/thinking display in the status panel — pull from get_state on open (cheap) or skip for v1?
  • Toast on background dead, or badge-only? (Today: toast. Keep unless noisy in practice.)
